# Semester Week 13 Progress Report

## Completed Work

- Exposed five tools to the model: `get_products`, `check_stock`, `analyze_sales`, `suggest_restock` (read) and `create_restock_draft` (write). The model selects the tools itself; nothing is routed by text matching.
- Wrote strict argument schemas with pydantic (`strict=True`, extra fields forbidden): types are not coerced ("7" is not accepted for `days`), ranges are enforced, and the model cannot send a file path or an `approved` flag.
- Defined a permission policy (`permissions.py`): four tools are read-only; `create_restock_draft` is the only write action, needs human approval, and may only write inside `outputs/drafts/`. The file name is generated by code and checked with `safe_join`.
- Implemented `create_restock_draft`: it validates items, rejects duplicates and unknown SKUs, limits a quantity to 1000 and a draft to 2000 in cost, and writes nothing when anything fails.
- Implemented the first bounded orchestration loop (`agent.py`): the model requests tools, `execute_tool` validates and runs them, every `tool_call_id` gets a result, and the run stops after 8 model turns or 40 tool calls. A model failure is reported as a stop reason, not an exception.
- The test suite now has 82 tests, all passing, using a clearly labelled fake model (no API key).

## Problems Encountered

- In the approved plan run, the final text contradicts the trace. The answer lists only SKU-1003 and SKU-2002 as running out within 14 days, but SKU-1001 (4.7 days left) is also in the draft, and the text says the draft covers "the three products above" although only two are listed above. The tool results and the draft file are correct; the summary text is wrong.
- For "Reorder SKU-9999." the model did not call `check_stock`, so it never learned that the product does not exist.
- The model chooses a different tool sequence on different runs of the same request (with and without `analyze_sales`), so results are not fully reproducible.
- Deciding where approval must live: if the model could pass `approved=true`, it could approve its own write action.
- A model can send several tool calls in one turn, and every call needs a result, including when a limit stops the run.

## Solutions

- Approval is decided by the application (`approver`), after validation, and the flag is set in `Env`, which the model cannot influence. A test checks that the tool schema has no path or approval field.
- Strict schemas with `extra="forbid"` turn invalid arguments into an error the model can read and retry; a test covers a retry.
- The loop answers all pending calls with `tool_call_limit` before stopping, so the message history stays valid. Tests cover denied approval (nothing written), approver failure (treated as denied), path escape, budget cap, step limit and tool-call limit.
- For the unknown SKU I added a rule to the system prompt: always call `check_stock` for a named SKU first and report `unknown_sku`. Rerun (`outputs/week-13-unknown-sku-v2.json`): the model called `check_stock({"sku": "SKU-9999"})`, got `unknown_sku`, and answered that SKU-9999 does not exist and no reorder was created (2 steps, 1 tool call, no draft). This is one run, so it shows the rule works at least once, not that it always will. The first three demos used the earlier prompt; only this demo was rerun.
- The text-versus-trace inconsistency is not fixed yet. Planned for Week 15: a check that every SKU and number in the final answer appears in the tool results, and that the draft contents match the answer.

## What I Learned

- A model only requests tools; permissions, validation and approval must live in my code, not in the prompt.
- Validation should be strict at the boundary: a string "7" or `True` must not pass as an integer, and unknown fields must be refused.
- A tool schema is also a security boundary: fields the model cannot see or set cannot be abused.
- Correct tool results do not guarantee a correct final text: the model can summarise them wrongly, so answers need their own check against the trace.
- Bounded loops need two limits (model turns and tool calls), because one turn can contain many calls.
